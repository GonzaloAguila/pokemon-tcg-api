# CLAUDE.md — pokemon-tcg-api

Backend for **Nostalgic TCG** (browser Pokémon TCG, Base Set + Jungle; Fossil and Team Rocket integrated on `feature/fossil-team-rocket`, not deployed). Express + Socket.io + Prisma/PostgreSQL. Serves REST for accounts/economy/collection and runs authoritative multiplayer games and drafts over Socket.io.

## Related repos (all siblings under `D:/Proyectos/`)

| Repo | Role |
|------|------|
| `pokemon-tcg-game-core` | Game engine, consumed from GitHub Packages at an **exact** version. The frontend must pin the same version so single-player and multiplayer run identical rules. Auth: repo `.npmrc` only sets the `@gonzaloaguila` registry; the token lives in each machine's `~/.npmrc` (`//npm.pkg.github.com/:_authToken=...`). |
| `pokemon-tcg` | Next.js frontend (Vercel). Talks to this API via `NEXT_PUBLIC_API_URL`. Holds the cross-repo orchestration notes and the VPS deploy skill (`.claude/skills/api-deploy/`). |
| `pokemon-tcg-landing` | Astro landing; only uses `POST /api/waitlist`. |

Change order when work spans repos: game-core (build, bump, publish) → API and frontend (bump to the same exact version).

**Local database:** local dev uses the Docker container `ptcg-dev-db` (`postgresql://ptcg:ptcg@127.0.0.1:55433/pokemontcg_dev`). Never point local `.env` at production — prod Postgres only listens on localhost on the VPS.

## Layout

- `src/index.ts` — Express app, router registration, Socket.io server, chat cleanup interval.
- `src/modules/<feature>/` — `*.controller.ts` (Router) + `*.service.ts` (+ `*.types.ts`, `index.ts` barrel). Modules: achievements, admin, auth (local + Google + Discord OAuth), battle-pass, boosters, bug-report, catalog, chat, decks, economy (v2: config, economy day, check-in, daily pack, pack inventory, missions, milestones, Fichas de canje, odds), market, matches (settlement), messaging, presence (public `GET /presence` → `{ online, registered }`), players (`GET /players/:username` + `/collection`: another player's public profile, signed-in only, banned = 404; `players.service.ts` selects are the whitelist, never add private fields), prizes, slots, users (+ rewards, XP, titles), waitlist, wheel. `game/` and `matchmaking/` are empty.
- `src/socket/` — `handlers.ts` (socket auth + event wiring), `rooms.ts` (`GameRoomManager`, in-memory games, `executeAction` switch), `draft-handlers.ts` / `draft-rooms.ts`, `state-masking.ts` (perspective swap for player 2, hidden zones, `REVEAL_RULES`), `schemas.ts` (zod schemas for every socket payload and game action), `session-guard.ts` (handshake auth + per-event account check), `io-registry.ts` (Socket.io server handle for HTTP code, e.g. kicking banned users), `presence.ts` (in-memory online users, one per user across sockets, and the global chat's `chat:presence { users, count }` list).
- `src/middleware/` — `auth.ts` (`requireAuth`, `requireRole`, `requirePermission`, `optionalAuth`, `checkUserStatus`), `error-handler.ts` (`AppError`, `Errors.*`), `rate-limit.ts` (auth routes only).
- `src/lib/` — `prisma.ts`, `jwt.ts`, `oauth.ts`, `password.ts`, `email.ts` (Resend), `account-state.ts` (15s cache of tokenVersion/role/status used by HTTP auth and sockets; admin moderation invalidates it).
- `prisma/schema.prisma` — 25 models. `Match` rows are written and settled once per game (`modules/matches`); `GameRoom` is unused. `prisma/migrations/`: baseline (applied in prod, adopted 2026-10-13) + `20261013000000_match_settlement` + `20261014000000_economy_v2` (both pending in prod until the economy-v2 release; `docs/migrations.md`); `test/migrations.test.ts` fails if the schema changes without a migration.

## Conventions

- Validate request bodies with zod in the controller; throw `Errors.BadRequest/NotFound/Forbidden/...` (instances of `AppError`) so `errorHandler` maps the status. Plain `Error` objects become 500s.
- Protect routes with `requireAuth` then `requireRole(...)` / `requirePermission(...)`. Superadmin bypasses permission checks. Economy actions (purchases, claims, spins, market, battle pass, achievement claims, economy v2: daily pack, opening inventory packs, Fichas de canje, set milestones) also take `requireVerifiedEmail` (403 `{ error: { code: "EMAIL_NOT_VERIFIED", message }, code, message }`; OAuth accounts count as verified: `lib/email-verification.ts` `isEconomyVerified`). Login, profile reads, deck building, playing and `POST /economy/check-in` don't; grants that don't go through a guarded route give an unverified account nothing instead (check-in: no login day/packs/coupons/battle-pass step and the day stays unclaimed; settlement: stats and XP but no match coins or missions, `emailVerified: false` in the result). New economy routes must take it.
- Socket identity: always derive the user from the verified handshake JWT via `getAuthUserId(socket)` (`handlers.ts`); never trust a `userId` in the payload. New socket events: parse the payload with a schema from `schemas.ts` (`parsePayload`) and, if it acts on games/rooms/chat/drafts, gate it with `requireSocketUser`/`checkSocketSession` (`session-guard.ts`). New game actions: add them to `gameActionSchema`; `executeAction` rejects anything the schema doesn't know.
- HTTP identity: `requireAuth` checks the token against `account-state` (tokenVersion, ban/suspension, current role). To revoke sessions, bump `tokenVersion` and call `invalidateAccountState(userId)` (+ `disconnectUserSockets`). Password reset and change do this (change returns fresh `accessToken` + cookie for the current session). Emails go through `lib/email.ts` `deliver`, which turns Resend's `{ error }` results into `EmailDeliveryError`.
- Any balance change must go through `users.service` (`creditBalance`/`debitBalance` or the `addCoins`/`spendCoins`/… wrappers): they do one atomic UPDATE (debits guarded by `balance >= amount`), reject non-positive amounts and log a `Transaction` row with its `currency`. Pass the transaction client (`db`/`tx` arg) so a purchase charges and grants in ONE `prisma.$transaction`. One-time claims use conditional `updateMany` (e.g. `unlockedAt: null`) and check `count`.
- Any change to a player's cards (`userCard` create/upsert/update/delete) must also call `recordCardChange` (`src/modules/users/card-ledger.ts`) in the same transaction: one `card_transactions` row per event (pack, trade, draft…) with `[{ cardDefId, quantity }]` (+ received, − given). `test/card-ledger.test.ts` fails if a file writes `userCard` without it. Admins read it at `GET /admin/users/:userId/card-history`.
- Prize games (wheel, slots) roll and grant server-side (`src/modules/prizes/`, CSPRNG); never accept a prize or outcome from the client.
- Economy v2 (`docs/economy-v2.md` is the frontend contract): every tunable number lives in `src/modules/economy/config.ts` (`ECONOMY`), never inline. Every daily/weekly/monthly thing uses the "economy day" (00:00 America/Argentina/Buenos_Aires = 03:00 UTC; weeks start Monday) from `economy/economy-time.ts` — never UTC dates. One-time claims (check-in, daily pack, welcome, milestones, Rare Candy weekly slots) go through `claimOnce` (`EconomyClaim`, `INSERT ... ON CONFLICT DO NOTHING`) inside the same transaction as the grant; take the user's row lock (`lockUsers`, id order) before read-modify-write of per-user counters (missions) and before any write that references a user by foreign key in a transaction that also locks users (settlement locks before claiming the match, whose `winnerId` is an FK; the drafted-cards credit locks before its upserts): out-of-order user locks deadlock and the loser transaction's grant is lost. Free packs go to the `UserPack` inventory (`economy/pack-inventory.ts`), never opened at random. A finished game only "counts" (stats, ranking, achievements, XP, match coins, missions) if it passes `ECONOMY.antiFarming` (turn ≥ 3, ≥ 2 min, ≤ 3 counted wins/day vs the same opponent; AI: ≥ 3 min, 10/day); every game end must go through `settleRoomResult` / `settleMatch`. Table bets are off (`ECONOMY.tableBets.enabled`; the server forces 0).
- Tutorial / puzzle progress (`modules/progress`, `UserProgress`): `GET /progress`, `POST /progress/tutorial/:lessonId`, `/progress/tutorial/claim`, `/progress/puzzles/:puzzleId`. Completion is client-reported, so items unlock in order and rewards (`ECONOMY.progress`) are small and once-only (`claimOnce` "tutorial"; a puzzle pays only when its row insert counts 1). `progress/catalog.ts` is mirrored by the frontend's `src/domain/scenarios/catalog.ts`: change both.
- User-facing strings (errors, event log messages) are Spanish; code and comments English.
- Card IDs: `{set-slug}-{3-digit-number}-{slug-name}`, e.g. `base-set-025-pikachu`, `jungle-002-electrode` (`Nidoran♀` → `nidoranf`, `Mr. Mime` → `mr-mime`).
- Card sets come from game-core's registry: `CARD_SETS`, `ALL_CARDS`, `findCardById`, `findCardDefinition(set, number)`, `getSetById`. Never write `[...baseSetCards, ...jungleCards]`. Catalog sets, draft pools and market/prize pools follow the registry automatically; a set's booster is one entry in `SET_BOOSTERS` (`boosters.service.ts`; prizes/battle pass pick from `STANDARD_BOOSTER_IDS`).

## Multiplayer model

- Game and draft rooms live in memory (Maps). A restart/PM2 reload drops every live game; reconnection only works within the same process. Single process only (no Redis adapter).
- Server keeps state from player 1's perspective; player 2's actions run on a game-core `swapSides` copy that is swapped back (`executeForPlayer` / `toActor` in `executeAction`), and `getGameStateForPlayer` (state-masking) uses the same `swapSides` plus "Jugador 1/2" swapped in the log. Pending choices (`pendingForceSwitch`, `pendingSelfSwitch`, `pendingDeckSearch`, `pendingBenchDamageSelection`, `pendingTypeShift`, `pendingPeek`) are NOT swapped: they belong to the side whose turn it is (engine convention), only that side may resolve them (turn gate in `executeAction`), and masking strips them for the other player and spectators.
- `pendingAttackChoice` (Hyper Beam, Terror Strike, Prophecy, Wildfire, Energy Conversion, Scavenge) is answered with `resolveAttackChoice { selection: string[] }` by the step's chooser only: the attacker (side whose turn it is) for `chooser: "self"`/absent, the OTHER player for `"opponent"` (Terror Strike, accepted off-turn). The server always applies game-core's `resolveAttackChoice` on the attacking side's view with `skipEndTurn`, then `endTurn(state, true)` once no choice is left. While one is pending every other action except `promote`/`takePrize`/`surrender` is rejected. Masking: the chooser gets it in full (Prophecy's top cards, even of the opponent's deck); everyone else gets `{ effect, step: { title, description, chooser, options: [], maxSelections, minSelections }, waiting: true }`. Step wording (also `pendingTrainerChoice`): `title`/`description` always speak to the card's player / attacker, so the waiting stub keeps them; the answerer of a `chooser: "opponent"` step receives game-core's `stepForAnswerer(step)` (its `title`/`description` already replaced by `answererTitle`/`answererDescription`). The frontend just renders `step.title`/`step.description` and never needs the `answerer*` fields.
- Promotions and prizes: `promote` is accepted from whichever side has `playerNeedsToPromote` in its view (off-turn too). `promote` / `takePrize` end the turn (`finishTurnAfter`, from the turn side's view) only when the turn was waiting for them: the side whose turn it is already attacked (`attackedThisTurn`) or endTurn paused after the checkup (`checkupDoneOnTurn === turnNumber`), both Actives are back and no prize/promotion is pending. Mid-turn promotions (Curse KO → opponent promotes; `discardFromPlay` of an Active Mysterious Fossil / Clefairy Doll or Cowardice → own promotion) leave the turn going. `discardFromPlay { pokemonId }` runs game-core's `discardFromPlay`.
- Every emitted state goes through `maskGameStateForPlayer(state, "player1" | "player2" | "spectator")`, which hides the opponent's hand/deck/prizes (same-length `{ id, hidden: true }` placeholders) unless a `REVEAL_RULES` entry shows them (rules must ask game-core, never re-implement the card). Clairvoyance: `isHandRevealed(state, side)` shows that hand to the opponent and to spectators (face up = public). Here Comes Team Rocket!: `arePrizesRevealed(state, side)` shows both sides' Prizes to everyone. Never emit `room.gameState` raw.
- On-play powers (Summon Minions, Sneak Attack, Reel In: evolving, Pokémon Breeder, benching): game-core sets `pendingPowerChoice { pokemonId, powerName, step }`; the side whose turn it is answers with `resolvePowerChoice { selection }` (run on its view). Masked for everyone else as `{ pokemonId, powerName, step: { title, description, options: [], maxSelections, minSelections }, waiting: true }`. While pending only `resolvePowerChoice`/`promote`/`takePrize`/`surrender` pass.
- Server-run Trainer steps (TR contract §3: Challenge!, Rocket's Sneak Attack, any step with `chooser: "opponent"` or `reveals`): the client sends `startTrainer { cardId, selections }` with the steps it answered; the server checks them (`walkClientSteps`), builds the next step from the UNMASKED state with `getTrainerSteps`, keeps the answers in `room.pendingTrainer` (never in the state: Challenge!'s picks are face down) and stores `pendingTrainerChoice { cardId, trainerName, step, chooser }` in the state (`chooser` relative to the Trainer's player = side whose turn it is). `answerTrainerChoice { selection }` comes from whoever the step asks (off-turn included); when no step is left the server runs `playTrainerCard` on the Trainer player's view. Masking: full for the answerer (Sneak Attack's `step.cards` = the opponent's whole hand; worded for them via `stepForAnswerer`, see `pendingAttackChoice`), stripped + `waiting: true` for the rest. While pending only answering and `surrender` pass (also no `requestCoinFlip`). `playTrainer` / `usePower` reject answers to such steps. `requestKick` targets whoever the game waits on (`awaitedSide`, see room lifecycle).
- Rules live in game-core; `rooms.ts` only dispatches. Board actions: `playBasicPokemon` (`playBasicToActive` / `playBasicToBench { cardId }`), `attachEnergyCard` (`attachEnergy { cardId, pokemonId }`, Rain Dance included), `evolvePokemonCard` (`evolve { cardId, targetPokemonId }`, legacy `targetIndex` still accepted). Trainers: `playTrainerCard` (`playTrainer { cardId, selections }`); activated powers: `usePokemonPower` (`usePower { pokemonId, selections }`). `selections: string[][]` answers the steps of `getTrainerSteps` / `getPowerSteps`; zod only bounds the shape, the engine checks every answer. Illegal moves throw `IllegalActionError`; `executeAction` returns `{ success: false, error: reason }` (Spanish) and leaves the stored state untouched. Check `canX` first when the error must not be thrown (e.g. before rolling coins).
- Coins are rolled server-side (`GameRoomManager`'s coin source: `crypto.randomInt` by default, injectable in tests via `new GameRoomManager(flipCoin)`). Attack, confusion and retreat coins go to the room via `showCoinFlip` (`{ attackName, results, count, flippedBy?, defenderResults? }`: `results` = the acting player's coins, `flippedBy` ("attacker"|"defender" per result, omitted = all the acting player) for Knock Down / Bench Manipulation (`plan.attackFlipper`) and Trainer/power coins (game-core's `getTrainerCoinFlippers` / `getPowerCoinFlippers`, `"self"`→`"attacker"`, `"opponent"`→`"defender"`: Digger alternates), `defenderResults` = Transparency / Final Beam coin). Sinkhole: `retreat` probes `executeRetreat` with heads (illegal retreat → rejected, no coin), then rolls `getRetreatDamageSources(view, "player")` coins and passes `{ coinResults }` (never omit them: the engine would use Math.random). Trainer/power coins (`getTrainerCoinFlips` / `getPowerCoinFlips`: Poké Ball, Heal) are requested BEFORE the steps with `requestCoinFlip { roomId, purpose: "trainer", cardId } | { roomId, purpose: "power", pokemonId }` (ack `{ success, results, result, flippedBy? }`), stored in `room.effectCoins` until the effect resolves (Trainer: per card instance, power: per turn) so they can't be re-rolled, then sent to the opponent/spectators as `showCoinFlip`. A client coin value is always ignored.
- Attacks: `canExecuteAttack` / `canExecuteMetronome` are checked BEFORE any coin (confusion included); then the server flips the coins of `getAttackCoinPlan(state, attackIndex | copiedAttack)` with `flipAttackCoins` (Smokescreen/Sand-attack coin, the attack's own — Stone Barrage until tails —, the defender's Transparency coin last; never `getAttackCoinFlipCount`, wrong for until-tails) and calls `executeAttack(state, i, { coinResults, skipDefenderPromotion: true })` / `executeMetronome(state, copiedAttack, { … })`; the engine resolves every coin effect, KOs and the end of the turn. Never add coin-effect logic to `rooms.ts`. After a KO the defender promotes and the attacker takes its prize (see promotions above). Metronome is only accepted on an attack with a `CopyAttack` effect. A transformed Ditto's attacks (and Metronome's copy target) come from game-core's `getEffectivePokemonCard`.
- Confusion is resolved in the `attack` action: server flips, `resolveConfusionFlip` (game-core) applies tails.
- The starting player draws on turn 1 inside game-core's `startPlayingPhase` (`playerReady` when both are ready); the API draws nothing itself.
- Decks used in rooms must pass `checkDeckPlayable` (owned by the player, rules + collection ownership). Only basic Energy is unlimited (game-core `isLimitedInDeck`: special Energy max 4); copies are summed per card id across variant entries (same-name cards of different sets are still counted apart, like the frontend builder).
- Room lifecycle: `joinRoom` never creates a room (missing → `error { code: "ROOM_NOT_FOUND", message }`); taking a seat (createRoom / a new joinRoom seat) needs a deck that passes `checkDeckPlayable`, reconnecting to your seat doesn't. A waiting room whose creator disconnects is hidden from the list at once and deleted after `WAITING_ROOM_GRACE_MS` (15 s) unless they rejoin; `deleteRoom` is by the creator's user id. A room `finished` / in GAME_OVER rejects every action and coin request. Every end path (game over, kick, disconnect/setup forfeit, draft forfeit) records the result once through `match-settlement.ts` `settleRoomResult` (`room.resultSettled`); in `handlers.ts` they share `finishRoomGame`. Mulligan only in MULLIGAN, without an Active and without a card playable as a Basic in hand (`hasBasicPokemon`); `playerReady` only in MULLIGAN/SETUP and with an Active.
- Awaited player (`rooms.ts` `awaitedSide`): in the opening the only player not ready; otherwise whoever owes a Trainer step / attack choice asked to them, a promotion or a Prize (both owe → nobody), else the side whose turn it is. Every emitted game state carries `awaitingUserId` (`room-state.ts` `maskRoomState`); `requestKick` only works against that player once the turn timer ran out.
- Drafts: admin actions (start, close) are by user id (`isRoomAdmin`: creator or admin seat; site admins may close from the backoffice: `draft:delete` acks `{ success, error? }` and emits `draft:roomDeleted` / `draft:error`); `draft:state` has `isAdminViewer`. Disconnected players never block: once only they are missing, `disconnectGraceMs` (10 s) then the server picks / bonus-picks / builds for them (`buildAutoDeck`, removal without a Basic). Bonus-pick (120 s) and building (600 s) have deadlines (`pickDeadline`). A room closed before its tournament refunds `entryPaidIds`; `keepInCollection` credits the drafted cards once (tournament end or close after the draft). `draft:forfeit` only from player1Id/player2Id of that game while it is playing.
- Conversion 1/2 (Porygon): the `attack` payload's `conversionType` is passed as `ExecuteAttackOptions.chosenType`; the engine applies it only for an attack with `ChangeWeakness` / `ChangeResistance` (`conversionEffect` is ignored). Prefer moving logic into game-core over adding more here.

## Backoffice rules

- Moderation and adjustments (ban, suspend, adjust-*, grant-cosmetic) go through `assertCanActOn` (`admin.service.ts`): never on a superadmin, on an admin only by the superadmin (403). A banned user can't be suspended (409). Deleting a user is refused while they sit in a game room or a draft (409); the delete removes the messages addressed to them (their self-sent welcome message included) in the same transaction. Prisma P2003 maps to 409.
- Player-visible wallet rows of admin adjustments say "Ajuste del equipo" (no admin id); cards and stats write no wallet row (the card ledger keeps `refId` = admin). Cosmetic grants only take ids from the API catalogs (`prizes/catalog.ts` + `ADMIN_ONLY_COINS`, set-milestone backs, every skin variant; free/starter items rejected).
- Welcome messages (`senderId = recipientId`) are automatic: excluded from the dashboard count and the admin list (`SENT_MESSAGE_FILTER`), not editable/deletable. Dashboard "day"/"week" use the economy day/week; the response carries `period` and `since`.

## Admin data fixes

For one-off grants (cards, currency) write a temporary `npx tsx` Prisma script, run it **on the VPS** from `/var/www/pokemon-tcg-api` (prod Postgres is localhost-only), then delete it. Prefer the atomic balance helpers so a Transaction row is logged, and `recordCardChange` (reason `admin_adjustment`) for cards. `userCard.upsert` with `update: { quantity }` *sets* the value; use `{ increment: n }` to add.
